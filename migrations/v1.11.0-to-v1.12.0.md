# v1.11.0 to v1.12.0

This release adds the organization operating layer under `organization/`:
`organization/AGENTS.md` and nine organization skills under
`organization/skills/` (`scout`, `implementer`, `validator`, `advisor`,
`orchestrator`, `multi-agent`, `ci-runners`, `workbench`, `git-etiquette`).
This repository becomes the governance layer for the whole agent runtime,
with two levels of agent instructions:

- **Organization layer** — `organization/AGENTS.md`, the role skills, and the
  organization skills, baked into the agent container image at user level,
  one level above every repository, and shipped with each container release
  (canary, then rollout). Each harness reads `AGENTS.md` directly or imports
  it from its user-level instruction file and loads the skills from its
  user-level skills directory.
- **Repository layer** — a repository's own root `AGENTS.md` carries only
  that repository's situational state; `.agents/skills/` and `paseo.json` add
  repository tooling.

Earlier releases put an organization block, `bedrock-organization`, into each
repository's root `AGENTS.md`. The organization layer replaces that block and
supersedes any such block a repository still carries.

The layer states that Paseo is the one multi-agent runtime; that role
profiles `scout`, `implementer`, `validator`, `advisor`, and `orchestrator`
carry the name of the role skill the started agent follows, with
`security-implementer` and `security-validator` as fallbacks used only after
the normal implementer or validator refuses a task on security grounds; that
agents run with full access inside their container and role skills give
guidance only;
that a Claude session ended by a usage limit is never resumed and is replaced
by a new session; that work autosaves as WIP commits pushed on every stop,
never on `main`, `master`, or `internal/main`; that heavy work runs on the
workbench under a 3-minute command cap and longer work on the GitHub test
runners; that web search and fetch use the Exa MCP tools; that secret values
stay unread and unprinted; and that pull requests stay open unless merging is
explicitly authorized. The role skills make the scout cite physical evidence
for every claim and declare the rest unknown, make the validator a bounded,
adversarial skeptic, and make the implementer work test first whenever
possible.

`manifest.json` gains an `organization` list with the path and SHA-256 digest
of every organization layer file. The repository's own `AGENTS.md` and
`README.md` describe the two levels and admit `organization/` as the one
location for organization-specific material. Publishing it is intended; the
one exclusion is personally identifying information — the operator's
machines, local folder paths, and usernames other than GitHub usernames.

The protocol files — the namespace `AGENTS.md` files and both templates — are
unchanged. Adopters resynchronizing through their protocol lock copy the same
bytes; no record migration is required, and existing records remain valid
unchanged.

These changes were selected by the organization's human authority on
2026-09-27. The role-to-model mapping of the profiles is Paseo configuration
recorded in the pull request, not part of the published files.

## Predeclared acceptance

1. Every protocol file listed under `files`, `root_protocol`, and
   `repository_block` has the same digest as in v1.11.0; any change fails.
2. Every file under `organization/` is listed under `organization` with a
   digest that matches its bytes; an unlisted file or a mismatched digest
   fails.
3. Each organization skill directory holds one `SKILL.md` whose front matter
   `name` equals the directory name and carries a `description`; any mismatch
   fails.
4. No organization layer file names the operator's machines, a local folder
   path, or a username other than a GitHub username; any occurrence fails.
5. No organization layer file forbids a tool or permission; role skills state
   what the role delivers and give guidance only. A sentence withholding a
   tool from an agent fails.
6. `organization/AGENTS.md` states each invariant listed above and a table
   naming which skill to read for which work; an omitted invariant fails.
7. `organization/AGENTS.md` and `multi-agent` state that implementation and
   validation start under `implementer` and `validator`, and that
   `security-implementer` / `security-validator` run the same brief under the
   same skills only after a refusal on security grounds; a fallback profile
   used first, or given its own skill, fails.
8. The release introduces no new record class, lifecycle state, checker, or
   gate.
