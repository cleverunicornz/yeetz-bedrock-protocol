# Protocol Decision: Bedrock 2.1.0, an additive release

## Choice

Bedrock 2.1.0 keeps every 2.0.0 meaning and adds four things, decided by the
organisation that owns the protocol, plus the tooling that enforces two of them.
The thirteen verbs, the five structural acts, the states, the transitions, the
outcomes and the roles are unchanged. Every act recorded under 2.0.0 stays valid.

1. **`Applies to` on Invariants and Promises.** An optional field naming what the
   record binds: `all environments` (the default when absent) or a version scope,
   a `system`-level scope such as `agent-runtime/2`. In the domain it is the
   making act's level and scope; in a file it is the heading `Applies to`.
   `binds(scope)` follows `belongs_to` from the scope to its version and to the
   organisation and returns what applies there.
2. **A Plan may hold Gaps.** Members are Candidates, Promises and Gaps. The work
   on a Gap member is `formulate` (and `refine`); its outcome is `decide`; a Gap
   member is complete when `decided`. `bad_member` no longer refuses a Gap.
   Recording a Gap assigns nothing, and a Plan assigns nothing by existing either;
   only a runtime's request assigns work, outside this protocol.
3. **Records live in the situation domain; files are projections.** A
   repository's `situation/` directory is where records are authored only until
   the domain holds them. A public repository then carries one generated file,
   `SITUATION.md`, a deterministic projection of its records at the repository
   level, rebuilt on every merge; a private repository carries none; a
   projection is never a source. The record templates become the domain's
   schema and the projection's format.
4. **The repository block of the root `AGENTS.md` is one fixed text**,
   `templates/repository-block.md`, with nothing filled in. The user-level
   protocol block is unchanged in meaning and is delivered to agents by their
   runtime.

The protocol repository is public and ships the enforcement for items 3 and 4,
so any repository under the protocol can call it: two reusable workflows and
their scripts, pinned to the protocol version a repository adopts.

## Why

- Rules and commitments differ between versions of a runtime; without a scope a
  rule for one version binds every version, and agents read rules that do not
  apply to them. Expressing the scope as the making act's level and scope adds no
  noun and no verb: `binds` already follows `belongs_to`.
- Work is often planned around an open concern before any Candidate exists.
  Holding the Gap in the Plan keeps that work visible without inventing a
  Candidate early. Completion stays a member property; the Plan still has none.
- Two authorities drift. Once the domain holds the records, files that agents can
  edit compete with it; a generated, never-edited projection gives readers outside
  the runtime the same records without a second source.
- Per-repository blocks drifted and duplicated graph knowledge. One fixed text
  sends every agent to the graph and lets a byte comparison enforce it.

## Rejected

- **A new noun or verb for scoping or Plan membership.** Rejected: both are
  expressible with the existing acts; a Bedrock change is reserved for meanings.
- **`Applies to` as a free field independent of the act's scope.** Rejected: it
  would let a record claim a scope it was not recorded in, and `binds` would need
  a second walk. The field, when present, must agree with the making act
  (`contract/examples/20-applies-to-a-version.yaml`).
- **Keeping the repository block template with placeholders.** Rejected: what it
  carried is graph knowledge and drifted per repository.
- **Shipping the checks in the organisation package.** Rejected: that package is
  private, and a private repository's reusable workflows cannot be called from
  public repositories.
- **Committing `SITUATION.md` with the head commit or today's date in its
  header.** Rejected: committing the projection would change the projection and
  the check would never settle. The header names the last commit that changed
  `situation/` and that commit's UTC date.

## Where the old repository block's content goes

| Old content | Where it lives now |
|---|---|
| Identity | The repository scope's context record in the graph |
| Ownership, and a fork's upstream coordinate | The same context record |
| Phase | The same context record |
| Graph scope and bootstrap | Given by the runtime with the request |
| Critical invariants | `binds` |
| Verification | `assured_by` and `open_work` |
| Tool priority | The tool tree the runtime gives |

Until the domain holds a repository's records, the context record is authored in
its `situation/` files like any other record.

## Exact changes

**Schema** (`contract/bedrock-v2.schema.json`):

- `properties.protocol`: `const "2.0.0"` becomes `enum ["2.0.0", "2.1.0"]`.
- New `$defs.applies_to`: `anyOf [{const: "all environments"}, {type: string,
  pattern: "^\S+$", minLength: 1, maxLength: 256}]`.
- `$defs.invariant.properties.applies_to` and
  `$defs.promise.properties.applies_to`: `{"$ref": "#/$defs/applies_to"}`,
  optional (not in `required`).
- `$defs.id_plan_member.anyOf` gains `{"$ref": "#/$defs/id_Gap"}`; its
  description names Gaps.

**Contract** (`contract/bedrock-v2.yaml`): `bedrock: 2.1.0`; `applies_to?` in
the Invariant and Promise fields; Plan members `[Candidate, Promise, Gap]` with
`member_work.Gap` and `assigns`; `refusals.bad_member` and
`structural_acts.regroup.members` name Gaps; `queries.binds` reaches a version
scope and the organisation; new sections `applies_to` and `records`. The prose
(`contract/bedrock-v2.md`) states the same in sections 3, 8 and 10.

**Templates**:

- `templates/repository-block.md` is the fixed text, byte for byte.
- `templates/records/` is new: one template per record class (Invariant, Gap,
  Candidate, Decision, Promise, Oracle, Witness, Reference, Plan), each a title
  line `# <prefix>-<number> — <title>` and the required headings in order, with
  optional headings marked `Optional.`. `Applies to` is optional on the
  Invariant and Promise templates only. `contract/check.py` proves each template
  states exactly its record's fields and links.
- `templates/root-protocol.md`: heading `Bedrock 2.1`, and a Plan is a group of
  Candidates, Promises and Gaps.

**Compiler**: admits stable `2.0.x` and `2.1.x` protocol and organisation
packages independently; renders the fixed repository block; `--repository` is
optional, still validated when given, and never rendered.

**Native replay**: the pinned receiver vendors the 2.0 contract.
`contract/tool-examples/replay.py` retracts exactly the additions above before
comparing; any other difference still fails. Receiver support for the additions
is a producer dependency this package does not claim.

## Tooling

- `.github/workflows/check-agents-md.yml` (`workflow_call`; input `version`,
  optional `runs-on`): downloads `bedrock-<version>.tar.gz` and `SHA256SUMS` of
  release `v<version>`, checks the archive against `SHA256SUMS` and every file
  against the manifest, then runs `scripts/check-agents-md.py`: the caller's
  root `AGENTS.md` must hold exactly one repository block equal to
  `templates/repository-block.md` byte for byte. The user-level protocol block
  is not checked.
- `.github/workflows/situation-projection.yml` (`workflow_call`; input
  `version`, optional `runs-on`, optional secret `push_token`): on a pull
  request of a public repository, verifies the release the same way, builds
  `SITUATION.md` with `scripts/situation-projection.py` and commits it to the
  pull request's head when it changed; on a pull request from a fork it fails
  with instructions, since it cannot push there.
- `scripts/situation-projection.py`: deterministic. Header: scope, source, the
  commit of the last change under `situation/` (security directories excluded),
  its UTC date and the words "projection; not a source of truth". Then
  Invariants, Promises with state, Oracles, Decisions, Gaps, Candidates, Plans,
  each in id order, and References as pointers. Repository level only; nothing
  under a `security` directory, no symbolic link, no Witness, no `context.md`.
  Same input, same bytes.
- `scripts/build-release.py`: builds the three release assets deterministically;
  it reproduces the published v2.0.1 archive byte for byte.

## Migrating a repository

1. Replace the repository block of the root `AGENTS.md` with
   `templates/repository-block.md`; move what the old block said into the graph
   as tabled above.
2. Call both workflows pinned to `v2.1.0` with `version: 2.1.0` (see
   `README.md`). A fork keeps its upstream's `AGENTS.md` and calls only the
   projection, if public.
3. Author new records in the shape of `templates/records/` until the domain
   holds them; give an Invariant or Promise `Applies to` only when it binds a
   version scope.

## Boundaries

The 2.0.0 and 2.0.1 tags, archives, manifests and records stay immutable;
`contract/patch-compatibility.md` remains the 2.0.1 commitment and its admitted
line is extended, not rewritten, by `contract/release-2.1.md`. SO117 remains the
unresolved observation in `contract/gaps/SO-000117-skill-verb-declaration.md`.
Releasing 2.1.0 activates nothing: no scope changes authority without its
qualification receipt, and Stage2 and Stage3 remain held.
